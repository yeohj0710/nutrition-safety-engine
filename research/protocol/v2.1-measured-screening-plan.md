# v2.1 작업 계획 — LLM 탐색 분류 추가와 파생 체인 반영

작성 2026-07-25. 프로토콜 v2.0(AI 기반 탐색적 문헌지도)을 유지한 채 **LLM 분류 층**을 더하고,
그 결과를 웹 도구까지 흐르게 한다. 데이터 재수집·연구질문 변경·사람 선별은 하지 않는다.

## 0. 프로토콜 준수 경계

v2.0 §5·§7·§9를 그대로 지킨다.

- 결과 라벨은 `retain` / `deprioritize` / `uncertain` 이며 사람의 include·exclude 가 아니다
- PRISMA 최종 포함·제외 수, 메타분석, RoB·GRADE, 임상 권고를 만들지 않는다
- **사람 gold standard 가 없으므로 민감도·특이도·정밀도·재현율·F1·정확도를 산출하지 않는다**
- 보고 가능한 것은 자동 방식 간 일치·불일치, 스키마 유효성, 계보 완전성, 재현성, 누출률뿐이다

지도교수 피드백(2026-07-20)도 사람 개입 더블체크 생략을 허용했고, 사용자는 전 과정을 AI로
수행하기로 결정했다. 따라서 이번 작업에 사람 판정은 포함하지 않는다.

## 1. 왜 필요했나

`ai_screening_classifications.csv` 의 `ai_method` 는 `deterministic_dual_profile_v1` 이다.
판정 근거가 `animal_term_present`, `population|exposure|outcome|human_signal` 같은 키워드
코드와 0~4점 점수이므로 **규칙 기반 분류기**다. 논문·발표에서 "AI 기반 분류"라고 부르려면
실제 언어모델 판정 층이 있어야 한다. 이번 작업으로 그 층을 만든다.

부수 효과로, 규칙 두 프로파일이 갈려 판단이 유보된 6,649행(32.9%)을 LLM 이 어떻게 나누는지
기술할 수 있게 된다. 이는 v2.0 §2의 연구질문 "AI 분류 일치·불일치를 기술한다"에 직접 답한다.

## 2. 구조

```
검색(PubMed, 확정 2026-07-13)
  └ evidence_map.csv  20,230 레코드-질문 / 초록 보유 18,015
       ├─ 규칙 기반 이중 프로파일 분류        (기존, 유지)
       └─ LLM 탐색 분류                      (신규)
            └ 두 방식 일치·불일치 기술
                 └ 정규식 PICOS 추출 + LLM 게이트
                      └ core evidence → 개인화 규칙 → 웹 도구
```

정규식 PICOS 필터는 문장 locator 와 용량을 뽑는 역할을 계속 맡는다. LLM 은 주제 적합성
판정만 맡아 **추가 게이트**로 동작한다. 둘 중 하나를 버리지 않는다.

## 2-1. 실행 현황 (2026-07-25 기준)

| 단계 | 상태 |
|---|---|
| LLM 탐색 분류 | **부분 완료 11,850 / 18,015 (65.8%)** — OpenAI 크레딧 소진으로 중단 |
| 방식 간 비교 | 완료 (부분 실행 기준, JSON 에 경고 명시) |
| 파생 체인 LLM 게이트 | **대기** — 커버리지 95% 가드가 부분 적용을 막고 있음 |
| 앱·테스트·빌드 | 완료 (테스트 148/148) |

**남은 작업은 명령 두 개다.**

```bash
python tools/llm_screening.py    # 체크포인트부터 이어서 실행
npm run research:refresh         # 비교 → PICOS+게이트 → core → 번들 재생성
```

크레딧을 채우기 전에는 1번이 즉시 429(`insufficient_quota`)로 끝난다.
런타임 AI 설명 계층도 같은 키를 쓰므로 현재는 결정론적 결과만 나온다(설계된 폴백).

### 부분 실행 결과 — 해석 주의

`research/synthesis/screening_method_comparison.json` 의 수치는 **무작위 표본이 아니다.**
대상 행을 `record_id` 순으로 처리했으므로 앞쪽 65%만 반영돼 있다. 전량 실행 후 반드시
재생성해야 하며, 그 전까지는 코퍼스 전체의 일치도로 인용하면 안 된다.

참고로 부분 실행 기준 단순 일치도 49.9%, Cohen κ 0.114 로 두 자동 방식의 합의는 낮았다.
규칙이 판단을 유보한 3,446행을 LLM 은 retain 43.2% / deprioritize 54.5% 로 갈랐다.

## 3. 단계

### 1단계. LLM 탐색 분류 — `tools/llm_screening.py`

- 대상: 초록 보유 18,015 레코드-질문 행
- 모델·추론강도·프롬프트 해시·입력 해시·토큰 사용량을 매니페스트에 기록
- 출력 `data/curated_v2/llm_screening_classifications.csv`,
  매니페스트 `research/screening/llm_screening_manifest.json`
- 체크포인트 JSONL 로 중단·재개 가능

### 2단계. 방식 간 비교 — `tools/compare_screening_methods.py`

- 교차표, 단순 일치도, Cohen's κ, 질문별 분포
- 규칙이 유보한 행을 LLM 이 어떻게 갈랐는지
- 출력 `research/synthesis/screening_method_comparison.json`
- **정확도 계열 지표는 산출하지 않는다.** JSON 에 `not_reported` 로 명시한다

### 3단계. 파생 체인 반영 — `tools/build_systematic_review_v3.py`

- LLM `retain` 을 추가 게이트로 적용
- `llm_decision` · `llm_confidence` · `llm_reason_codes` 를 추출 결과에 컬럼으로 보존
- 매니페스트에 `llm_gate`(적용 여부, 입력 해시, 정규식 통과 수, LLM 이 뺀 수) 기록
- 이후 `build_core_evidence_v3.py` → `personalized_rules` → 웹 도구까지 재생성

### 4단계. 검증과 배포

- typecheck · lint · vitest · build 통과
- 경계 테스트(`ai-exploratory-boundary`, `thesis-mode-boundary`, `legacy-mode-boundary`) 유지
- Vercel 배포 후 라이브 확인
